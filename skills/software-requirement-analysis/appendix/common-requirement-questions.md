# Common Requirement Questions

This document lists the question dimensions that should be asked to gather necessary information for software requirement analysis.

Questions are organized into three dimensions: **Action**, **Reaction**, and **Boundary**.
Each dimension focuses on a specific aspect of the software operation to ensure comprehensive requirement coverage.



## Action: Triggering and Causality

The Action dimension focuses on the conditions under which an operation can be performed, how it is triggered, and the expected behavior when it is executed.



- **Internal Behavior**
  What is the expected internal behavior of the system after this action is performed? This includes the ultimate state of the system, any persistent changes, and the overall outcome that should be achieved.
  The internal behavior refers to the system's internal state changes, processing logic and assistance such as the state migration, data release and the log record,.



- **Output Behavior**
  What is the expected output behavior of the system after this action is performed? This includes the ultimate state of the system, any persistent changes, and the overall outcome that should be achieved.
  The output behavior refers to the observable results or responses generated by the system as a result of this action. This includes changes in the user interface, notifications, or messages sent to other systems.



- **Enable/Disable Conditions**
  What's the conditions for enable/disable of these actions? If there are some related configurations for this action, what's the entrance, items and default values of these configurations.



- **Trigger Conditions**
  What's the conditions to trigger this action: in which object states is the operation allowed or disallowed? (For example: can an order in "cancelled" state be "Confirm Received"?)



- **Synchronous or Asynchronous**
  Is this operation synchronous (waits for a result in real time) or asynchronous (puts a message on a queue / background job)?



- **Repeated Triggers**
  If a user triggers the action repeatedly (e.g., double-clicks a button), should the system be idempotent and ignore the second trigger, return an "operation too frequent" error, or perform the action twice?





## Reaction: Paths and Side Effects

The reaction dimension focuses on the outcomes and side effects of an action, including success, failure, alternative paths, and any additional impacts on the system.



- **Success Path**
  What is the expected outcome when the action succeeds? For example: a new record is created, an existing record is updated, a message is sent, etc.
  How many possible paths can lead to a successful outcome? What the conditions are for each path? Are there any variations in the success outcome depending on the path taken?



- **Failure Path**
  What is the expected outcome when the action fails? For example: an error message is returned, a rollback is performed, etc.
  How many possible paths can lead to a failure outcome? What the conditions are for each path? Are there any variations in the failure outcome depending on the path taken?



- **Alternative Path**
  The alternative path should be not success path, but it also not a failure path, it likes a downgraded or partial outcome.
  Are there any alternative paths the system should take under specific conditions? (For example: if a stock is insufficient, should the system suggest alternatives or cancel the operation?)
  How many possible alternative paths exist? What are the conditions for each path? Are there any variations in the alternative outcomes depending on the path taken?



- **Side Effects**
  Are there any side effects that occur as a result of this action? (For example: updating related records, sending notifications, triggering other processes, etc.)
  How many possible side effects exist? What are the conditions for each side effect? Are there any variations in the side effects depending on the path taken?



## Boundary: Boundaries and Constraints

The boundary dimension focuses on the limits and constraints of an action, including state, temporal, data, and concurrency boundaries.



- **State Boundaries**
  In which object states is the operation allowed or disallowed? (For example: can an order in "Cancelled" state be "Confirm Received"?)



- **Temporal Boundaries**
  Are there any time-related constraints for this operation? (For example: must be completed within a certain time frame, only allowed during business hours, etc.)



- **Data Boundaries**
  For text fields, what is the maximum length? For numeric fields, what are min/max values? What does null/empty mean?



- **Concurrency Boundaries**
  When multiple people operate on the same data concurrently, use optimistic locking (version), pessimistic locking (row lock), or last-writer-wins?
