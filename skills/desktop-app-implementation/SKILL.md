# Desktop Application Implementation

本 Skill 将桌面应用的架构与功能设计转化为可运行、可验证的代码。实现应遵循项目既有技术栈和约定，优先使用仓库中的代码、测试及构建工具，不凭空假设框架能力或项目结构。

## 目标

- 根据需求和设计契约实现桌面端功能，保持与既有架构、模块边界和数据流一致。
- 严格遵守已锁定的 IPC/命令签名、数据结构、错误类型、持久化格式及层间接口。
- 以用户可见行为为验收依据，完成相关测试、类型检查或构建验证。
- 将实现限制在请求范围内；除非用户要求，不提交代码、不推送、不创建 PR。

## 基础准则

- 本 Skill 的所有问答优先使用交互式组件（如复选框、下拉菜单）进行提问；若平台不支持，则使用清晰的编号列表在聊天中提问。
- 当用户明确回答"没有其他问题"或"进入下一步"时，AI不得继续追问，必须进入下一步（避免无限循环）。但若本轮讨论中用户提出的新要点尚未达成共识，AI必须先回到相应要点继续讨论，直到所有已提出的要点均已确认，才能进入下一步。

## 输入与依据

按以下优先级确定实现依据：

1. 用户当前明确提出的需求和决策。
2. 用户提供或仓库中可确认的已批准功能设计契约、架构文档。

开始前检查相关设计文档和代码。功能设计文档中的锁定契约是接口实现的依据；架构文档决定技术栈、分层、模块通信和持久化边界。不得以“更方便”为由绕过这些约束。

若没有正式设计文档，但用户请求清晰且现有代码足以确定实现方式，可按仓库惯例直接实现。仅在缺少信息会导致不可逆的架构选择、行为歧义或违反已锁定契约时，才暂停并询问用户。发现设计文档与需求冲突、接口定义不完整或现有架构无法满足需求时，说明具体冲突和影响，不得自行更改契约；需要时建议先返回相应设计阶段修订。

## 核心约束

### 契约和架构

- 不得擅自修改已锁定的 IPC 命令/事件名称、参数、返回值、序列化字段、持久化格式及层间接口。
- 不得引入与架构决策冲突的新框架、语言、通信方式、存储方案或依赖方向。
- 若需求需要改变锁定内容，先明确指出变更项及其下游影响，等待设计契约更新后再继续。
- 复用项目已有抽象和错误处理方式；不得在 UI、应用逻辑和基础设施间随意复制职责。

### 桌面应用行为与安全边界

- 保持界面响应：耗时 I/O、网络访问、文件处理和 CPU 密集工作不得无意阻塞 UI 线程；遵循项目已有的异步、任务取消及进度通知模式。
- 对来自 UI、IPC、文件、网络或用户配置的数据，在其信任边界进行校验；校验失败时返回明确错误，不使用成功形状的默认值掩盖问题。
- IPC/插件/桥接接口仅暴露实现功能所需的最小能力；遵循框架已有的权限、命令注册和上下文隔离配置。
- 文件系统操作遵循应用已定义的数据目录和路径策略；不得将凭据、令牌或敏感用户数据写入日志或源码。
- 保持键盘可用性、可访问性、本地化和多窗口行为与项目现有约定一致。若需求涉及这些行为，不得以静默降级代替实现。

### 代码与文件操作

- 先检查再编辑，尊重工作区已有的用户改动；不得覆盖、回滚或清理与任务无关的内容。
- 使用当前环境可用的工作区编辑工具直接修改文件，不要把完整源文件仅作为聊天代码块交付。
- 仅新增或修改完成需求所需的文件；按现有命名、格式、依赖注入、状态管理和错误映射模式实现。
- 不添加不必要的抽象、配置选项、依赖或无关重构。只有在需求或现有模式要求时才改动打包、权限、升级或平台配置。

## 强制工作流

### S1：收集和检查

1. 解析用户需求，提取涉及的用户流程、验收行为、边界条件和目标平台。
2. 检查仓库指导文件、架构/功能设计文档、相关源文件、测试和构建脚本。
3. 确认该变更属于哪一层，追踪相关 IPC、状态、持久化和 UI 调用链。
4. 检查工作区状态，确保识别并保留已有未提交改动。

若请求范围明确且资料充分，直接进入实现；不要为了形式流程重复询问已知信息。

### S2：澄清关键阻塞项

仅针对无法从需求、设计文档或代码库可靠确定且会实质影响行为/架构的问题提问。优先提供清晰选项，并给出简短推荐理由。常见阻塞项包括：

- 目标操作系统或桌面框架无法从工程中确认。
- 设计契约缺少必需的接口、状态转换、错误行为或权限决定。
- 多窗口、离线、数据迁移、任务取消等行为存在多种互不兼容的解释。
- 改动可能破坏现有接口或需要用户批准的跨平台/架构取舍。

已由仓库或用户输入明确的信息不得再次询问。不要将普通实现细节升级为用户决策。

### S3：确定实现顺序

根据实际改动制定最小可行的实施顺序。涉及跨层功能时，通常先对齐类型和接口契约，再实现桌面端命令/服务与状态，然后接入 UI，最后补充测试和配置。对于简单变更可直接实施，不要求输出冗长计划或等待额外确认。

如发现计划将修改已锁定接口、引入新的依赖或改变用户可见行为，先暂停并征求用户决定。

考虑下述内容并将结果发给用户确认，并根据用户的意见进行修改后，方可进入实现阶段。

- 准备将代码划分为几个大模块，几个小模块或几个类，命名空间之类的组织结构。
- 每个模块的文件夹命名，路径；下面包含哪些源文件，这些源文件的命名。
- 确认各模块的职责边界、接口契约和依赖关系，避免循环依赖和职责混淆。
- 考虑现有的状态管理、异步处理和错误处理模式，确保新实现与之兼容。

### S4：实现

- 完成端到端行为，保持接口、后端处理、前端状态和用户反馈一致。
- 为加载、成功、空结果、失败及可重试场景提供符合设计的 UI 状态。
- 正确管理订阅、事件监听、后台任务和组件/窗口生命周期，避免重复注册、资源泄漏或过期结果覆盖新状态。
- 保持错误可诊断且对用户可理解；不吞掉错误，不以宽泛捕获或静默回退伪装成功。
- 同步更新与变更直接相关的测试、类型、文档及必要的工程配置。

### S5：验证与交付

1. 运行覆盖本次改动的最小现有测试、lint、类型检查或构建命令；只有针对性验证发现问题时再扩大范围。
2. 对用户可观察的行为进行验证。涉及多平台时，不得声称验证了未实际检查的平台。
3. 检查最终差异，确认没有改动无关文件、破坏锁定接口或遗漏错误路径。
4. 回复时简明说明完成内容、验证结果及任何未解决限制；不得声称未运行的测试或未验证的平台已通过。

若验证命令因缺少依赖或工具失败，只有在依赖清单已变更或确认为缺少所需工具时才安装/恢复依赖。对环境限制或既有失败应如实说明，不得隐藏。

## 技术栈适配

本 Skill 不绑定桌面框架。实现前识别并遵循工程实际使用的技术栈，例如 Tauri、Electron、Flutter、Qt 或其他框架：

- 遵循该框架既有的 IPC/插件注册、权限声明、序列化、线程/异步和打包模式。
- 遵循项目使用的 UI 框架、状态管理、路由、样式和测试工具。
- 不因本节示例而推断或更改项目技术栈；以工程配置和架构文档为准。

## 完成检查清单

- [ ] 用户需求及验收行为已落实；范围未擅自扩大。
- [ ] 已遵循架构决策和所有锁定的接口/数据契约。
- [ ] UI、后台处理、错误反馈及资源生命周期保持一致。
- [ ] 安全边界和用户数据处理遵循现有策略。
- [ ] 相关测试或验证已运行，未验证项已明确说明。
- [ ] 工作区中与任务无关的改动均已保留。
